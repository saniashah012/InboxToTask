CP2 classification rules:
- Exactly one category for the CURRENT message: Actionable if any outstanding request, owner's commitment, necessary assigned next step, or explicitly requested conditional action exists. Otherwise Passive.
- Mixed information and requests is Actionable. Extract every distinct outstanding user action. Conditions and alternative response branches belong to that action; do not double-count "confirm or ask to reschedule" as two obligations. Do not assume the user accepts an interview.
- Optional events, promotions, newsletters, and informational links are Passive unless context establishes a commitment or required response. Urgent marketing does not establish an obligation.
- Someone else's promise is Passive/waitingFor unless there is also a separate owner responsibility. Tasks contain ONLY obligations of the inbox owner; owner is exactly user.email. External commitments go into waitingFor, with the responsible person/address.
- Use CURRENT thread state: no tasks for requests the supplied history shows completed or canceled. Do not merge separate assignments or infer shared dependencies merely from similar wording. Existing user decisions are context; any extracted changes are proposals, not authorization to overwrite.
- A conditional reminder explicitly requested in an email is an Actionable task with its condition preserved, even before the trigger occurs.
- Suggested follow-ups are separate from explicit tasks. Only suggest one for a Passive waitingFor item with an explicitly promised date already passed at analysisTime and no resolution visible in supplied history. Cite that limited visibility. With no promised date, do not invent a follow-up threshold. Reference the zero-based waitingForIndex and correct recipient.

Extraction:
- Deadline null if unspecified ("soon" is not an exact date). Never invent dates, hours, duration, grades, effort, priority, acceptance, or completion.
- Interpret relative dates from the MESSAGE SENT DATE, not today's date; use user.timeZone unless the email explicitly specifies another zone. Flag ambiguous dates/ownership/time zones in uncertainties. Unknown hour is null. Preserve "before" boundaries, periods such as "afternoon", conditions, and dependencies in wording/requirements. A meeting date is not automatically a task deadline.
- Give date as YYYY-MM-DD and time as HH:mm or null. Each deadline includes an IANA timeZone, original wording, and boundary (by/before/on/unspecified). Do not convert "before 4 pm" into an inclusive 4 pm deadline.
- Evidence must be a short verbatim substring of the named supplied message BODY. Never fabricate quotations or cite excluded messages. Each task/waitingFor/follow-up needs its own supporting evidence. Current-message classification evidence must cite the current message.
- confidence is a self-reported 0-100 classification score, NOT a calibrated probability or proof of correct fields. Use uncertainties for actual limitations.
- summary is one short factual sentence, retained for the informational digest. No duplicate long narrative or chain of thought. No separate global priority reasoning: application code can sort known deadlines, keep undated actions visible, and separate conditional tasks.
- The input's contextWarnings must appear in uncertainties when nonempty. Never assume unavailable history is complete. Missing context warrants Needs Review rather than invented resolution or obligations.
